# ADR-013: Events that are not an AutoSE trigger get their own concurrency group

- **Status:** Accepted. Supersedes the concurrency rule in ADR-010. The recorded runs do not include a second trigger waiting on the same issue, so this rule was not what decided a result.
- **Date:** 2026-11-20

## Context

ADR-010 sets the group to `autose-issue-<issue number>` with `cancel-in-progress: false`, so a second trigger waits. The group is declared at workflow level, so it applies to every `issue_comment` event on that issue, including an ordinary comment that starts no run.

GitHub keeps at most one pending run per concurrency group. When a new run arrives while one is running and another is pending, the pending one is cancelled. An unrelated comment on the issue can therefore replace a queued `/autose` run. It also appears as a skipped run in the Actions list. This was found while writing the workflow, from the concurrency documentation, before any run.

## Decision

The group expression returns `autose-issue-<n>` only when the event is a real trigger: the label `autose` on an issue, or a comment that starts with `/autose`. Every other event gets `ignore-<run id>`, a group nothing else shares. The `gate` job still checks the actor's permission, so a non-writer who types `/autose` can still occupy the issue's group briefly and cause a queued run of a writer to be replaced. The gate then stops the stranger's run in seconds.

## Alternatives considered

Concurrency at job level inside `analyst` only. The later jobs would not be serialised, and a second run could push the same branch while the first is releasing.

A lock held by a branch or a label on the issue. It needs write access from the gate job and has to be cleaned up on failure, which adds state ADR-004 avoided.

## Consequences

The one remaining weakness is the one named above: a stranger's `/autose` comment can replace a writer's queued run. The writer re-triggers it. The cost is one comment, not a spend of the Gemini key, because the gate stops the stranger's run before any model job. A fix would be to check the actor in the concurrency expression, but `author_association` of a comment is the only permission-like field available there and ADR-010 chose the stricter collaborator permission lookup.

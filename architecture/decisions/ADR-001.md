# ADR-001: Three model roles, and a script for release

- **Status:** Accepted. The role split ran on every finished issue, including [run 44799110233](https://github.com/Anilkumark17/tinydb/actions/runs/44799110233). The model names in the table were superseded by ADR-014 and ADR-015.
- **Date:** 2026-11-20

## Context

The assignment fixes six stages and asks how many agents should cover them. One agent can hold the issue, the spec, the diff, the pytest log, and the review in one conversation. Six agents, one per stage, repeat the same repository read and pay for six cold starts. The reviewer is required to be independent of the implementer, so at least that cut is mandatory.

TinyDB's change surface for these issues is small. Issue 1 is a doc-id comparison in `Table.update` and `Table.remove`. The planning stages read the same files the coding stages edit. The release stage pushes a branch and opens a pull request. That is a `gh` invocation with inputs that are already known.

## Decision

Four roles:

| Role | Stages | Model |
| --- | --- | --- |
| Analyst | 1 Requirements, 2 Design | `gemini-2.5-flash` |
| Implementer | 3 Implementation | `gemini-2.5-flash` |
| Tester | 4 Testing | `gemini-2.5-flash` |
| Reviewer | 6 Review | `gemini-2.5-pro` |

Stage 5 is a script. It does not call a model.

The analyst stays one process across stages 1 and 2 because both stages are read-only and the design is a refinement of the spec. The stage-1 script still has to pass before the process may write `design.md`.

The implementer and the tester are different processes. The tester writes tests from `spec.md`. It receives the diff and, on a retry, the pytest log. It does not receive the implementer's messages. A single process that both edits `tinydb/` and writes the tests can satisfy the tests by narrowing them to whatever the edit already does.

## Alternatives considered

One agent for all six stages. The review then sits in the same conversation as the implementation, which is the failure mode ADR-008 exists to prevent. A retry of stage 3 also resends the whole history.

One agent per stage, six model calls. Stages 1 and 2 would each re-read `ARCHITECTURE.md` and the issue, and the only new input to stage 2 is `spec.md`, which the analyst just wrote. The extra call buys a context cut we do not need until the reviewer.

An agent for release. The model would choose the base branch, the title, and the `gh` arguments. The base branch has to be `master` for `ci-workflow.yml` to run. A script that takes the title from the first heading of `spec.md` and calls `gh pr create --body-file` has no opportunity to retarget the pull request or to merge it.

## Consequences

A test failure returns to the implementer with a log, not with a shared memory of why the edit was written. That is deliberate. It also means the implementer can repeat a bad edit if the log is thin. The retry budget in ADR-009 is what stops that loop.

Release cannot invent a pull-request body that hides a failing test. The body is the spec's acceptance criteria plus the link to `test_report.md`. The script refuses to push when pytest's exit code is non-zero.

The reviewer is the only role on `gemini-2.5-pro`. Cost and the reason for that split are in ADR-006.

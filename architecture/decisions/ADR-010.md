# ADR-010: A writer starts one run per issue, and the pull request targets master

- **Status:** Partly superseded by ADR-013. On issue #2, comments that started with `/autose` did not start a run. Adding the label `autose` did.
- **Date:** 2026-11-20

## Context

The assignment's sketch starts the workflow on `issues: [labeled]` and on `issue_comment: [created]`. Both events are delivered for any user who can open an issue or comment on a public repository. The actor who adds the label is not always the actor who wrote the issue.

`master` is the default branch and the base named in `ci-workflow.yml` (`pull_request.branches: [master]`). `main` exists and points at the same commit, `edff96a`, and it is protected the same way. A pull request into `main` would not start that CI workflow. Stage 5 would then wait for a check that never runs.

Two triggers can arrive close together: a label and a `/autose` comment, or two comments. Both would otherwise push `autose/issue-<n>`.

The workflow's own release script comments on the pull request. That comment must not start another run.

## Decision

The workflow runs when either of these is true:

- `issues` type `labeled`, and the label name is `autose`.
- `issue_comment` type `created`, the comment body starts with `/autose`, and the comment is on an issue. A comment on a pull request does not start a second implementation. Review of an open pull request is the review job of the run that opened it.

The actor must have `write` or `admin` permission on the repository. The `issues: labeled` payload carries the issue author's `author_association`, not the labeler's, so the gate job looks up the labeler with `gh api repos/<owner>/<repo>/collaborators/<sender.login>/permission`. For `issue_comment`, the comment's own `author_association` (`OWNER`, `MEMBER`, or `COLLABORATOR`) is also checked, and the same permission lookup is used so both triggers follow one rule. Anyone else can open an issue and can write a label name inside the body. They cannot start the run. The association that is checked is the person who applied the label or wrote the comment, not the issue author.

Comments whose author is `github-actions[bot]` are ignored.

Concurrency group is `autose-issue-<issue number>`, with `cancel-in-progress: false`.

The release script opens the pull request with base `master` and head `autose/issue-<issue number>`, branched from `master` at the run's start. It does not open a pull request against `main`.

## Alternatives considered

Let any commentator start the run, so the five issues can be launched from a fresh account for a demo. The issue body is already untrusted. Adding an untrusted trigger means a stranger can spend the Gemini budget and push branches. The maintainer can still start a run on an issue that a stranger wrote. That keeps the "anyone can report a bug" path and drops the "anyone can spend the key" path.

Trigger on pull-request comments as well, so `/autose` on the pull request re-runs the review. That matches the sketch's second line more literally. It also lets a review comment that quotes `/autose` re-enter the builder. Issue comments are enough for the five issues. A pull-request comment can be added later by superseding this ADR if a demo needs it.

Open the pull request against `main` because the assignment text says "protect the main branch." Protection is on both branches. CI is on `master` only. Targeting `main` would make stage 5's CI check fail for every issue, including a correct patch. `master` is the branch the project already treats as the integration branch.

Cancel the older run when a second trigger arrives. The newer issue text would win, which is attractive if the maintainer edited the issue and re-labeled. It also aborts a push. The maintainer who wants a clean restart can wait for the first run to finish or fail. ADR-004 already makes the next run start from stage 1 with the issue text as it is then.

## Consequences

The first real run is started by the owner adding `autose` to one of issues 1 to 5, or by the owner commenting `/autose` on that issue. A fork of this fork does not receive `GEMINI_API_KEY`, and this workflow is not started from `pull_request` events, so a pull request opened from outside does not get the secret.

If `master` and `main` diverge later, new branches still come from `master`. `main` can remain a protected mirror of the pin or can fall behind. The workflow does not try to keep them equal.

A collaborator who can apply a label can spend the key. That is the same group who can push branches. It is the group the assignment calls the maintainer.

The label has to exist before the first run. Creating the `autose` label is part of bringing the workflow up, not part of this decision's runtime check. The gate compares the label name as a string. It does not create the label.

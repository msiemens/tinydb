# ADR-017: Fall back to Groq when Gemini stays unavailable

- **Status:** Accepted. Extends ADR-015; Gemini stays the primary model.
- **Date:** 2026-11-20

## Context

[Actions run 44784749664](https://github.com/Anilkumark17/tinydb/actions/runs/44784749664) passed the gate and the analyst, then the builder stopped on `Gemini HTTP 503: This model is currently experiencing high demand`. The client had already retried three times over about 35 seconds. The overload was on the provider side, and the whole run was lost to it.

## Decision

`autose/llm.py` keeps Gemini as the first call for every role. When Gemini still returns 429, 500, 502 or 503 after its retries, and the secret `GROQ_API_KEY` is set, the same request goes once to Groq's chat-completions API with model `openai/gpt-oss-120b`, with the same retry rule.

The client translates the request and the response, so the tool loop, the tools and the prompts are unchanged. Each usage line records the model that actually answered, so `results/` shows which calls were served by Groq.

`GROQ_API_KEY` is passed only to the steps that already receive `GEMINI_API_KEY`. No step that runs model-written code gets it (ADR-012).

## Alternatives considered

Switch every role to Groq. That changes the model behind the earlier runs and makes them harder to compare, and Groq's free tier has tight per-minute token limits for the builder's long tool loops.

Only lengthen the Gemini backoff. That helps with short spikes but still loses the run when an overload lasts minutes.

## Consequences

A run can mix two models. The usage log shows where, and the report must say so for any run that fell back.

If both providers fail, the run stops as before.

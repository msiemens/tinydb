# ADR-007: Scripts and pytest decide. The reviewer decides only its own verdict.

- **Status:** Partly superseded by ADR-011, ADR-016, and ADR-019. The stage scripts did run. Stage 5 no longer requires a fully green matrix. ADR-019 waits only on pull-request checks and collects only `tests/`.
- **Date:** 2026-11-20

## Context

Each stage has a check that must pass before the next stage starts. The model that wrote the artifact has an interest in the check passing. An LLM judge of a spec, asked of the same model that wrote the spec, will often agree with it. Pytest does not.

The existing CI workflow runs a large matrix, including coveralls, on pull requests into `master`. "The code builds" is a smaller question than "the full CI matrix is green." The assignment lists those as different checks: stage 3 builds, stage 4 runs the test suite, stage 5 waits until CI passes.

`Table` imports cleanly today. A syntax error in the patch is what stage 3 has to catch. Behaviour belongs to stage 4.

## Decision

| Stage | Check | Who decides |
| --- | --- | --- |
| 1 | In `spec.md`, every acceptance criterion is a bullet that contains both a condition and an observable result. A bullet that is only an adjective fails. At least two criteria are required, matching the hidden-test floor. | A Python script in the analyst job. One regeneration on failure, then the job exits and uploads `spec.md` with the script's message. |
| 2 | `design.md` contains at least one path that exists in the checkout and at least one `def <name>` that occurs in that file. | A Python script. Same one-regeneration rule. |
| 3 | `uv sync --group dev` and `uv run python -c "import tinydb"` both exit 0. | The shell exit code. No regeneration inside stage 3. A broken import stops the run. |
| 4 | `uv run pytest` exits 0. The report lists the summary line and, on failure, the node ids. | The pytest exit code. |
| 5 | `gh pr view` reports `OPEN` and base `master`. The Checks API reports the `ci-workflow` conclusion `success` for that head SHA. The wait is bounded, see ADR-009. | `gh` and the Checks API. A timeout is a failure, written into `pr.md`. |
| 6 | `review.md` begins with `verdict: approve`, `verdict: code`, or `verdict: approach`. `code` and `approach` include a path that exists in the diff. | The reviewer model chooses the word. The script rejects a missing or unknown word and does not substitute `approve`. |

The stage-1 script does not call Gemini. A criterion is testable when a later pytest can fail on it, which means it names what is done and what should be true afterwards. The script looks for that shape. It does not try to prove the criterion is the best reading of a vague issue. Issue 5 will pass the script if the analyst picks a measurable reading, including the reading already used by the hidden tests, and it will also pass for a different measurable reading. The hidden tests are not an input to the script.

## Alternatives considered

An LLM judge for stages 1 and 2, with a different prompt called "critic." It can catch a criterion the script treats as well-formed and that is still vague. It can also pass the analyst's wording because it is the same family of model. The script is strict about shape and blind to sense. That blindness is acceptable because stage 4 and the hidden tests punish a spec that is measurable and wrong.

Treat a green `import tinydb` as optional and rely on pytest. A patch that does not import never reaches a useful pytest report. The import check makes that failure a stage-3 failure, which matches the assignment's column for stage 3.

Mark stage 5 successful when the pull request is open, and let CI finish in the background. The assignment's check is that CI passes. Skipping the wait would report success for a pull request whose tests are still red. The bound on the wait is there so a hung matrix does not hang the run forever. A hung matrix is recorded as a failed check, not as a pass.

## Consequences

The stage-2 script will accept a design that names `Table.search` for an issue that should edit `Table.update`, as long as both the file and the function exist. Existence is the check the assignment asked for ("names the files and functions"). Correctness of the plan is what `verdict: approach` is for.

Issue 5 can produce a spec the script accepts and the hidden tests reject. That gap is intended. The hidden tests are the grader's oracle, not the workflow's oracle.

Coveralls runs inside `ci-workflow.yml` and may fail when its token is absent. If it does, stage 5 will fail closed and `pr.md` will say which check failed. Silencing coveralls would be a change to the project's CI, not a change to this gate. If that happens on the first real run, ADR-007 should be superseded with the evidence, not quietly edited.

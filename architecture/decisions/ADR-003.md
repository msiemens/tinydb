# ADR-003: Hand off artifacts, and withhold the builder's reasoning

- **Status:** Accepted. The hand-off was used on the finished runs. Hidden tests were run by a person afterwards. On issue #2 the reviewer approved a diff that does not fix the issue.
- **Date:** 2026-11-20

## Context

Each stage needs enough to do its work, and no more. The assignment is specific about the reviewer: it sees the issue, the diff, and the repository at the pull request's head. It may run the code. It does not see the implementer's conversation. The same pressure applies, one step earlier, to the tester. A grading copy of the hidden tests lives at `experiment/hidden_tests/`, and the issue texts live at `experiment/issues/`, because that is the submission layout. Those directories are not a hand-off. Every file-reading tool refuses a path under `experiment/`.

Assignment 2's `ARCHITECTURE.md` describes Python-Markdown. This fork is TinyDB at `edff96a`. Handing the analyst that document would name `markdown.preprocessors` and `Registry`, which are not in this tree.

Issue bodies are written by whoever opens the issue. They are data, not instructions. ADR-009 covers how that is enforced. This record covers what is included.

## Decision

| Receiver | Receives | Does not receive |
| --- | --- | --- |
| Analyst | Issue title and body inside an `untrusted` fence. `ARCHITECTURE.md` at the repo root. A read-only checkout of `master`. | Hidden tests. The reviewer's later notes, on the first pass. Any secret. |
| Implementer | `spec.md`, `design.md`, write access to the checkout, and on a retry the pytest traceback or the review's file list. | The tester's prompt, the reviewer's conversation, hidden tests. |
| Tester | `spec.md`, `design.md`, `diff.patch`, and on a retry the pytest log. | The implementer's messages. Write access outside `tests/`. |
| Release script | Branch name, the spec's first heading, a `test_report.md` whose recorded exit code is 0. | A model, and therefore no chance to reinterpret a failure as a pass. |
| Reviewer | The issue title and body, `git diff` of the pull request against `master`, a fresh checkout of the pull request head. Permission for the workflow to run pytest. | `spec.md`, `design.md`, `test_report.md`, builder logs, the analyst's messages, hidden tests. |

`spec.md` and `design.md` are Actions artifacts. They are not committed. If they were committed, the reviewer's checkout of the pull request head would include them, and the restriction above would be a prompt line the model can ignore by opening the file.

The tester is allowed to see `spec.md` because its job is to write one test per acceptance criterion. The reviewer is not allowed to see `spec.md` because the assignment defines its inputs as the issue and the diff. The issue is the product request. The spec is the analyst's interpretation of it.

## Alternatives considered

Commit `spec.md` and `design.md` on the branch so a restarted job can read them without artifacts. That makes the hand-off durable and makes the reviewer able to read the analyst's plan. ADR-004 stores those files as artifacts instead, and accepts that a new run starts over.

Give every agent the full conversation so far. Debugging would be easier. The tester and the reviewer would inherit the implementer's justification and would tend to confirm it.

Give the analyst the Assignment 2 architecture document plus this tree. The document is the wrong system. The root `ARCHITECTURE.md` in this fork is the replacement, written from `database.py`, `table.py`, and `storages.py` at `edff96a`.

## Consequences

The reviewer can still open tests that the tester committed, because those tests are part of the diff. That is allowed: the assignment says the reviewer sees the diff. It can notice a test that does not match the issue. It cannot see the hidden tests, so a pass on the pull request is not a pass on `experiment/hidden_tests/`.

The implementer, on a review retry, sees a file list and the verdict, not a paragraph of advice about how to rewrite the function. The point of the return edge is to name the place that is wrong. A long coaching note would put the reviewer in the implementer's seat.

If `design.md` names the wrong file, the implementer will follow it. The stage-2 script checks that the named file and function exist. It does not check that they are the right place to edit. That judgement is the analyst's, and a wrong plan comes back through `verdict: approach`.

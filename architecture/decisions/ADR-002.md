# ADR-002: A fixed Actions pipeline decides the back-edges

- **Status:** Partly superseded by ADR-011. The pipeline ran. None of the five finished issues took a back-edge. Every posted verdict was approve.
- **Date:** 2026-11-20

## Context

Something has to decide when stage 4 returns to stage 3, when stage 6 returns to stage 2 or stage 3, and when the run stops. The candidates are a model acting as planner, a Python state machine inside one job, or GitHub Actions jobs wired with `needs` and `if`.

The back-edges are already fixed by the assignment. Tests fail: retry implementation, and if they keep failing, reconsider the design. A review that objects to the approach returns to design. A review that objects to the code returns to implementation. At most two review rounds. A human merges.

GitHub's default `GITHUB_TOKEN` on this repository is read-only. A job that needs to push must set `contents: write` on itself. A single job that both reviews and pushes would hand the reviewer a token that can push. That collides with ADR-008.

`ci-workflow.yml` already defines the project's own test matrix. This workflow should not re-implement that matrix. It should open a pull request and then read the check that the existing workflow produces.

## Decision

The workflow file is the controller. Jobs are `gate`, `analyst`, `builder`, `release`, and `review`. The builder job contains the implementer process, the tester process, and the pytest step, and it loops internally up to the budget in ADR-009. Review rounds are two copies of the review path (`review` and, when the verdict asks for another round, `review_again`), not a model choosing the next job.

A job starts only when the previous stage's check file says `pass`. The analyst does not get to declare stage 1 finished. The builder does not get to declare pytest finished. The rules are in ADR-007.

Who sends work backward:

| Observation | Who notices | Where it goes |
| --- | --- | --- |
| Spec or design script failed | The analyst job, after one regeneration | The run stops. The artifact says which check failed. |
| `import tinydb` failed | The builder job | The run stops. No pull request. |
| pytest failed, retries left | The builder job | The implementer process, with the pytest log. |
| pytest failed, retries spent | The builder job | The analyst process once, then one more build. Then stop. |
| `verdict: code` | The review job's script | The builder job, if this is round 1. |
| `verdict: approach` | The review job's script | The analyst job, if this is round 1. |
| `verdict: approve`, or round 2 is done | The review job's script | Stop. The pull request stays open. |

The controller is not allowed to merge, close the pull request, or delete the branch.

## Alternatives considered

A planner model that picks the next stage. It can skip the reviewer, treat a failed pytest as a pass, or keep going after two review rounds. The stages are a known graph. Paying a model to rediscover that graph adds a place for the issue text to inject a new edge.

One Python process for every stage, including review and push. Loops are easier to write. The process that can push is the process that reviews, so reviewer independence becomes a prompt instruction instead of a permission.

Chained workflows that trigger each other with `workflow_dispatch`. Each hop is visible as its own run, which is pleasant to debug, and each hop must re-authorize the actor and re-find the artifacts. The back-edge budget would be split across runs and would be easier to exceed.

## Consequences

The YAML will contain a repeated review job rather than a loop construct Actions does not have. That repetition is the record of "at most two rounds." A reader can see both rounds without opening a trace.

A bug in the `if` conditions can skip a stage. The stage-map checks are the mitigation: each job exits non-zero when its check file is missing or says `fail`, and `needs` will not start the next job.

The builder job holds both the implementer and the tester so the pytest retry does not need a new Actions job per attempt. They are still separate processes, with the hand-off from ADR-003. The job permission stays `contents: read`. Push waits for the release job.

# ADR-011: The release step uses a repository-scoped token so CI starts

- **Status:** Accepted. Supersedes the release credential in ADR-002, ADR-005 and ADR-007 (stage 5). Release opened pull requests #19, #22, #25, #26, and #27, and CI started on them.
- **Date:** 2026-11-20

## Context

ADR-007 makes stage 5 pass only when the `ci-workflow` check on the pull request succeeds. ADR-005 gives the release job `GITHUB_TOKEN` with `contents: write` and `pull-requests: write`.

GitHub does not start new workflow runs for events caused by `GITHUB_TOKEN`, except `workflow_dispatch` and `repository_dispatch`. A branch pushed and a pull request opened by the release job would therefore never start `ci-workflow.yml`. Stage 5 would wait for a check that does not exist, then time out on every run. This was found while writing the workflow from the ADRs, by reading the GitHub Actions documentation on `GITHUB_TOKEN`, before any run. The three earlier ADRs did not consider it.

`ci-workflow.yml` has no `workflow_dispatch` trigger. Adding one means editing the project's own CI file, which this workflow must not touch.

## Decision

The release and `release_again` jobs check out and push with the secret `AUTOSE_PAT`: a fine-grained personal access token limited to `Anilkumark17/tinydb`, with Contents and Pull requests read and write, and nothing else. They fall back to `GITHUB_TOKEN` when the secret is missing. In that case the stage fails after five minutes with the message "no CI check started", so the cause is visible in `pr.md`.

Only the two release jobs receive the token. The review jobs keep `GITHUB_TOKEN` with `contents: read` and `pull-requests: write` and run without credentials in the checkout. The release step also refuses a patch that touches `.github/`, `autose/` or `.git/`, so the token cannot be used to change the pipeline through a model-written diff.

## Alternatives considered

Add `workflow_dispatch` to `ci-workflow.yml` and trigger it from the release job. It keeps `GITHUB_TOKEN`, but it edits a file outside this workflow, and a dispatched run is not attached to the pull request as a check.

Run the project's tests inside our own job and treat that as CI. This does not check the project's real matrix, and it duplicates `ci-workflow.yml`, which ADR-002 chose not to do.

Skip the CI condition in stage 5. The assignment's check for stage 5 includes that CI passes.

## Consequences

One long-lived secret exists that can push branches and open pull requests in the fork. It cannot merge past branch protection, which requires a pull request. A leaked token would let someone open pull requests and push `autose/*` branches. It would not let them change `master` directly. The token should be given a short expiry.

The five-minute grace and 25-minute wait for CI are unchanged from ADR-009.

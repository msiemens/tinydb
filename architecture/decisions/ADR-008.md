# ADR-008: The reviewer is a separate job, model, prompt, and token

- **Status:** Accepted for the separate job, prompt, and token. The separate model did not survive ADR-015: the reviewer used `gemini-3.5-flash-lite`, the same id as the builder. On pull request #22 that reviewer approved a patch the hidden tests reject.
- **Date:** 2026-11-20

## Context

A reviewer that can read the implementer's reasoning tends to approve the conclusion it has just been walked through. A reviewer that can push can "fix" the branch instead of sending it back, or can approve and merge. The assignment forbids both. The maintainer is the only one who merges.

Prompt text is the weakest of the available fences. The model can be told to ignore the builder and can still agree with it if the builder's argument is in the context. The fences that hold are the ones the model cannot see past: a new process, a checkout that does not contain the planning artifacts, a model id that is not Flash, and a process environment with no git credentials and no `GITHUB_TOKEN`.

Rubber-stamp approval is the remaining failure. An empty context does not force the model to look at the diff. A review that says only "looks good" is not a review.

## Decision

The review runs in the `review` job.

- The job checks out the pull request head SHA, not the builder's workspace.
- The prompt file for this job is separate from the analyst, implementer, and tester prompts. It states the inputs: the issue, the diff, the tree. It states that a merge is not available.
- The model id is `gemini-2.5-pro`, as in ADR-006.
- The model process environment contains the checkout path and the issue text. It does not contain `GITHUB_TOKEN`, `GEMINI_API_KEY`, or a git remote URL with credentials. The runner supplies the key on the server side of the API call.
- After the model writes `review.md`, a script posts it as a pull request review comment. That script is the step with `pull-requests: write`. The model does not run it.
- `contents: write` is absent on the review job.
- The script rejects `verdict: approve` when the body does not name at least one file from the diff and one behaviour from the issue that the reviewer checked. A rejection here does not flip the verdict to `code`. The round counts as used, `review.md` records the script's reason, and the run stops for a human if this was round 2. If this was round 1, the reviewer is asked once more, with the same inputs plus the line that the previous approval was rejected for being empty. It is not given a hint about what to object to.

The reviewer's tools are list directory, read file, and `run_tests` (ADR-005). `run_tests` takes no arguments, so the model cannot choose the command. The runner runs the fixed pytest command. A failure is appended to the reviewer's next message inside the same review round. It is not a license to edit the branch.

## Alternatives considered

A second prompt in the builder job, called "now pretend you are the reviewer." The transcript is still in the process. This is the design the assignment is written to rule out.

A second workflow file triggered by `pull_request` from the release. The separation is even clearer in the Actions UI. The trigger would also fire for human pull requests, and the artifact hand-off of `state.json` would cross workflow runs. One workflow with a job boundary is enough separation for the token, and it keeps the round counter in one place.

Require the reviewer to find at least one defect before it may approve. That would stop rubber stamps by forbidding approval. It would also force a false defect onto a correct patch. The check is that the reviewer names what it inspected, not that it must complain.

## Consequences

A Pro reviewer can still approve a wrong patch after naming a file. The file-naming rule catches an empty approval. It does not catch a wrong one. The hidden tests and the maintainer are the remaining checks. The workflow's job ends when the reviewer approves.

The reviewer cannot see `spec.md`. If the analyst narrowed issue 5 to a behaviour the issue text does not state, the reviewer judges the diff against the vague issue, not against the analyst's reading. Those two judgements can disagree. That disagreement is a reason to return `verdict: approach`, which is the outcome we want when the spec over-fits.

Posting the review is a write to the pull request, done by the script. The model cannot post a second comment, cannot request a reviewer account, and cannot approve through GitHub's review API. GitHub's formal "Approve" on the pull request is not used. `review.md` is the record. The maintainer still has to merge, including when the verdict is `approve`.

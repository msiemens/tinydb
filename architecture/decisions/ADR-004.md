# ADR-004: Artifacts hold run state, the branch holds code

- **Status:** Accepted. Stage artifacts were uploaded on the finished runs and were not committed onto the pull-request branches.
- **Date:** 2026-11-20

## Context

A later job on a later runner cannot see the previous job's disk. GitHub offers three relevant stores: files committed on the branch, workflow artifacts, and the Actions cache. Pull-request comments are a fourth store, visible to humans and to anyone the workflow later trusts.

This repository's `master` is protected. A direct push to `master` is rejected. The workflow is allowed to push a new branch and open a pull request. It is not allowed to merge.

The five issues can be started twice, by a label and by a comment, or by two clicks. A restarted run must not mix a new issue body with an old spec.

## Decision

| Store | What goes there | What does not |
| --- | --- | --- |
| Actions artifacts, one per stage | `spec.md`, `design.md`, `diff.patch`, `test_report.md`, `pr.md`, `review.md`, and `state.json` | Secrets, the Gemini key, raw model transcripts |
| The feature branch `autose/issue-<n>` | The source edit and the tests under `tests/` | Spec, design, review, transcripts |
| Pull request | The url, recorded in `pr.md`, and the review comment posted from `review.md` | The only copy of a stage artifact |
| Actions cache | Nothing for this workflow | Dependencies are installed by `uv sync` in the job. Caching them is an optimisation for later, not state. |

`state.json` holds the issue number, the branch name, the pytest attempt count, the design-return count, and the review round. The next job downloads the artifacts by name. It does not scrape the log.

A re-run of the workflow starts at stage 1. It does not download artifacts from an older run id. The issue may have been edited. An old spec would hide that edit.

Concurrency is one in-progress run per issue number. A second trigger waits. It does not cancel the first run. Cancelling mid-push can leave `autose/issue-<n>` updated and the pull request missing.

## Alternatives considered

Commit every artifact onto the branch. A human reading the pull request would see the spec beside the code, and a restarted job would not need artifacts. The reviewer checkout would then contain `spec.md` and `design.md`, which breaks ADR-003. The branch would also contain the analyst's words in a commit the maintainer is asked to merge.

Store state in pull-request comments and parse it back. Comments are easy to read on the issue page and easy to forge. The next run would be one edited comment away from `attempt=0` or `verdict=approve`.

Use the Actions cache as the hand-off. The cache is keyed for dependency reuse, may be evicted, and is shared more widely than a named artifact of one run. It is the wrong lifetime for a spec.

## Consequences

A failed run still leaves its artifacts for the maintainer to open, which is the assignment's requirement that a run be understandable from the artifacts and the pull request. A failed run before stage 5 leaves no pull request. The artifacts are the whole record in that case.

`state.json` can drift from the real pytest exit code if a job writes it by hand. The builder writes `attempt` only after pytest returns, and stores the exit code in the same file. The release job reads that exit code and will not push on a non-zero value, even if a prose report says the tests passed.

Waiting rather than cancelling means two clicks on the same issue run one after another and cost two analyst calls. That cost is the price of not interleaving two pushes to `autose/issue-<n>`.

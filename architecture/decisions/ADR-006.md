# ADR-006: Flash writes the change, Pro reviews it

- **Status:** Superseded by ADR-014. The first Actions run returned HTTP 404 for `gemini-2.5-flash`.
- **Date:** 2026-11-20

## Context

The repository secret is one Gemini key. A model-list call against that key returned `gemini-2.5-flash` and `gemini-2.5-pro`, among others. There is no second provider key, so a reviewer from another vendor is not available without a new secret.

The assignment allows one model for every role. It also says a different model for the reviewer is worth considering, because a reviewer that shares the author's blind spots will agree with it.

Flash is the cheaper and faster of the two. A full run is one analyst call, one or more implementer calls, one or more tester calls, and one or two reviewer calls. The coding calls dominate the count. The review calls are the ones that must be willing to disagree.

TinyDB issues in this set are local edits to `Table`. They do not need the larger model to find `table.py`. They need a careful reader at the end, looking at a diff with no stake in having written it.

## Decision

| Role | Model | Why this one |
| --- | --- | --- |
| Analyst, implementer, tester | `gemini-2.5-flash` | Several calls per issue. The stage checks are scripts and pytest, so a weak patch fails even when the model is confident. |
| Reviewer | `gemini-2.5-pro` | One or two calls per issue. A larger model, a different prompt, and a context that excludes the builder's notes. |

Temperature is left at the provider default and is not varied between roles. Changing temperature would make two runs harder to compare and would not separate the reviewer from the builder.

No run uses a preview or TTS model from the same key. The model id is fixed in the runner, not chosen from the issue text.

## Alternatives considered

Pro for every role. The review would be stronger, and so would the bill. Five issues, with retries, on Pro is the wrong default under a small monthly cap. The checks on stages 1 to 5 do not need the larger model in order to fail a bad patch.

Flash for the reviewer as well. One model id is simpler, and the permission split in ADR-008 would still hold. The reviewer would share Flash's failure modes. The only independence left would be the empty context. That is necessary and not sufficient. ADR-008 keeps the empty context either way. This ADR adds a second model id on top of it.

A second provider for the reviewer. That is the stronger experiment. It needs a second secret we do not have. If one is added later, this ADR should be superseded rather than edited in place.

## Consequences

A Flash implementer and a Pro reviewer can still share training data and still both miss a TinyDB invariant. The model change reduces same-model agreement. It does not create an independent implementation.

The runner must send the model id. If the id is omitted, the provider's default might be Flash for the reviewer too, and this ADR would be silently void. The review job fails closed when the response does not identify `gemini-2.5-pro`.

Cost is reported later as token counts from the runner, not estimated here. This record only fixes which model is allowed to spend those tokens.
